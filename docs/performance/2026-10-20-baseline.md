# Windows baseline frozen before optimization

Measured 2026-10-20 on the real interactive Windows desktop using unchanged original application source `6c85be6` (application code identical to `75516d6`). The full protocol and predeclared comparison thresholds are in [the frozen protocol](2026-10-20-protocol.md). Per-trial statistics are archived in [the baseline JSON](2026-10-20-baseline.json). Raw data remain outside Git at `E:\EasyTranslate-implementation-notes-20261020\benchmark\runs-baseline\cold-1` through `cold-7`. Reproduce and analyze with [the benchmark runner](README.md).

The 7 new-process/profile launches, 30 warm invocations, one deliberate empty invocation and two 30-second idle intervals completed. Each call used the actual global Alt+Q shortcut, foreground native WinForms TextBox, real existing PowerShell copy helper, original selection service, Electron popup, preload/Vue, real OpenAI-compatible adapter, synthetic in-process 50 ms transport and isolated JSON history. No real provider credential/network was used; no installed application was replaced. All application config/history/userData were in the run directories.

The foreground HWND equaled the source form HWND at 37/38 shortcut emissions. Three attempted selected-text captures returned empty `copy-timeout` (one first, two warm), so results were 6/7 first and 28/30 warm. One warm timeout (cold-1-invoke-10) already had a different foreground HWND at emission, demonstrating desktop interference or a failed focus transfer in that attempt; the other two started with the expected foreground. Those attempts showed an empty popup and did not call the adapter or add history. The foreground was not sampled continuously during the helper: the shared user desktop could change focus after emission. The evidence therefore establishes observed native copy timeouts under these conditions, not a proven application bug or proof of a first-trigger readiness failure. Every successful nonempty capture reached the expected visible result; no successful captured first trigger was observed lost.

The deliberate empty selection took 1812 ms through capture and 1823 ms to popup show, returned `copy-timeout`, made no translation request and created no history. Text, HTML and RTF clipboard fixtures were restored after all 38 captures. Image restoration and unsupported clipboard formats were not tested here. The baseline main document has no explicit application-ready handshake; document loading and native `show` must not be interpreted as interactive readiness or actual painted pixels. DOM-result timestamps prove mutation availability with visibility state `visible`, not photometric display latency.

## Full application process tree resources

The external .NET sampler resolved actual parent relationships and sampled every native helper PID (38/38) as well as Electron main, renderers, GPU and utility descendants. Sum working set may count shared pages more than once; private bytes are also reported. Normalized CPU = summed process CPU delta / wall time / 16 logical CPUs. The sampler itself is external and excluded from app resource totals; its cost was typically 51 ms per approximately 100 ms sample, and its contention is a limitation shared by the future comparison. Launcher health telemetry every 500 ms also adds overhead. Baseline and comparison must use this same instrumentation.

| Phase (first 2 seconds excluded) | Samples / duration | CPU normalized | Private MiB P50/P95 | Working set MiB P50/P95 | Processes P50 |
|---|---:|---:|---:|---:|---:|
| Before first popup, background hidden | 257 / 27.933 s | 0.070% | 222.36 / 230.08 | 350.71 / 358.18 | 4 |
| After 30 repeats and empty popup | 256 / 27.886 s | 0.273% | 274.59 / 340.54 | 502.55 / 535.76 | 5 |

The after interval contained both visible and hidden popup samples (visible windows P50=0, P95=1); it must not be described as a fully hidden background-only interval. Steady process count returned to 5 (P95=5, maximum 6 transient). Maximum across the long run was 9 descendant processes, 434.76 MiB private bytes and 647.32 MiB summed working set, including transient native helper descendants. Exactly two BrowserWindows were created and maximum live windows was two across all 32 invokes in that process. This shows no per-translation window accumulation in this sample; it does not measure every renderer subscription/timer or prove absence of memory leaks.

History contained the expected maximum 20 retained synthetic entries in the long run, one entry in each other successful cold run, and none in the cold run whose capture timed out. All retained content matched synthetic source/result fixtures. Every app run exited with code 0; managed source forms and app processes were stopped, and supported original clipboard data were restored from memory by the outer runner.

## Fixed comparison gates

Use the frozen protocol unchanged: first-popup local latency P50 should improve without added first-trigger loss; warm path P50/P95 must stay within max(15%, 50 ms) of corresponding successful-path baseline (show 902/1036 ms; DOM 963/1104 ms), while independently reporting all attempted capture outcomes. Entire-tree idle CPU stays <= max(baseline+0.5 percentage points, 1%). Steady private bytes stays <= 274.59 + max(15%, 30 MiB) = 315.78 MiB after first-popup steady state; hidden preheat's extra renderer cost must also be reported against the 222.36 MiB pre-popup state. No linear window/process growth across repeated translations. The selection PowerShell helper is a measured major cost; preheating is expected to reduce only the post-capture first-window cost (240 ms P50 to DOM here), not third-party latency.

These measurements establish the pre-optimization gate for T1; typed-build/packaged and final comparison evidence is recorded separately. They do not constitute NSIS installation verification, Linux runtime testing or real provider API validation.
